# OCare — 건강활동 데이터 수집 백엔드

삼성헬스 / 애플 건강(HealthKit)이 App to App 으로 단말에 전달한 걸음수·칼로리·이동거리 데이터를
서버에서 수집·저장하고, 사용자 구분 키(`recordkey`) 기준으로 일별/월별 집계를 조회하는 백엔드입니다.

## 로컬 실행

### 1. MySQL · Redis 기동

```bash
docker compose up -d
```

`docker-compose.yml` 이 아래 두 컨테이너를 띄웁니다.

| 컨테이너 | 포트 | 비고 |
|---|---|---|
| `ocare-mysql` | 3306 | 타임존 `Asia/Seoul`, charset `utf8mb4` |
| `ocare-redis` | 6379 | |

최초 기동 시 `docker/mysql/init.sql` 이 실행되어 스키마 두 개가 생성됩니다.

- `ocare` — 애플리케이션용
- `ocare_test` — 테스트 전용

기동 상태는 아래로 확인합니다.

```bash
docker compose ps
```

### 2. 애플리케이션 실행

```bash
./gradlew bootRun
```

기동 시 Flyway 가 `V1`~`V3` 마이그레이션을 적용합니다.

### 3. 테스트 실행

```bash
./gradlew test
```

163 개 테스트가 실행됩니다. MySQL·Redis 컨테이너가 떠 있어야 합니다.
테스트는 `@ActiveProfiles("test")` 로 실행되어 `ocare_test` 스키마와 Redis DB 1 번을 사용합니다.
개발 중이던 데이터가 테스트에 오염되거나, 반대로 테스트가 개발 데이터를 지우는 일을 막기 위함입니다.

## 설정

접속 정보는 모두 환경변수로 덮어쓸 수 있습니다. 미지정 시 아래 기본값이 적용됩니다.

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `MYSQL_URL` | `jdbc:mysql://localhost:3306/ocare?...` | JDBC URL |
| `MYSQL_USERNAME` | `root` | DB 계정 |
| `MYSQL_PASSWORD` | `root` | DB 비밀번호 |
| `REDIS_HOST` | `localhost` | Redis 호스트 |
| `REDIS_PORT` | `6379` | Redis 포트 |
| `JWT_SECRET` | 로컬 개발용 기본값 | **배포 시 반드시 교체** (HS256, 32바이트 이상) |

테스트용으로는 `TEST_MYSQL_URL`, `TEST_MYSQL_USERNAME`, `TEST_MYSQL_PASSWORD`,
`TEST_REDIS_HOST`, `TEST_REDIS_PORT` 를 사용합니다.

### 타임존

수집 데이터의 집계 기준일(`measured_date`)이 KST 기준이므로, 타임존을 세 곳에서 일관되게 고정합니다.

1. MySQL 컨테이너 — `TZ=Asia/Seoul`, `--default-time-zone=+09:00`
2. JDBC URL — `serverTimezone=Asia/Seoul`
3. Hibernate — `spring.jpa.properties.hibernate.jdbc.time_zone=Asia/Seoul`

한 곳이라도 어긋나면 일별 집계 경계가 하루씩 밀립니다.

### 스키마 관리

스키마의 소유권은 Flyway 마이그레이션에 있으며, Hibernate 는 `ddl-auto=validate` 로 검증만 수행합니다.
`DECIMAL` 정밀도나 `UNIQUE` 제약이 Hibernate 의 자동 DDL 로 어긋나는 것을 막기 위함입니다.

## 동작 흐름

```
회원가입 → 로그인(JWT) → 레코드키 등록 → 데이터 수집 → 일별/월별 조회
                                            ↓
                              정규화 → 중복 제거 → 원본 저장 → 집계 갱신
```

레코드키는 단말이 발급하는 사용자 구분 키입니다. 등록 시 회원과 매핑되며,
수집·조회 모두 **요청자가 그 레코드키의 소유자인지 확인한 뒤** 처리합니다.
인증(로그인했는가)만으로는 부족하고, 인가(그 데이터의 주인인가)까지 확인해야 하기 때문입니다.

## 입력 데이터에서 확인한 문제와 처리

제공된 4개 파일(총 4,710 구간)을 먼저 분석해 아래 네 가지를 확인하고 설계에 반영했습니다.

### 1. 두 출처의 시각 표기가 다릅니다

```
삼성 : "2024-11-15 00:00:00"        오프셋 없음
애플 : "2024-11-14T21:20:00+0000"   ISO8601, UTC
```

오프셋이 없는 값을 UTC 로 읽으면 9시간이 밀려 하루 경계가 통째로 어긋납니다.
오프셋이 없으면 기기 로컬(KST)로 간주해 UTC 로 변환하고, 집계는 KST 날짜(`measured_date`)로 합니다.
UTC 기준으로 집계하면 매일 오전 0~9시 활동이 전날로 밀립니다.

원본에 오프셋이 있었는지를 `source_offset` 에 남겨, 서버가 **추정**한 데이터를
나중에 식별할 수 있게 했습니다.

### 2. 걸음수의 JSON 타입이 다르고 소수가 섞여 있습니다

```
삼성 : "steps": 54                    숫자
애플 : "steps": "688.5509846105425"   문자열, 소수
```

`BigDecimal` 로 받으면 두 표기를 모두 처리할 수 있어 별도 역직렬화기가 필요 없습니다.
소수 걸음은 원본 그대로 저장하고(`DECIMAL(12,6)`), **집계 시 합산을 마친 뒤 한 번만 반올림**합니다.

구간별로 반올림하면 원본 합계와 어긋납니다. INPUT_DATA4 의 2024-11-16 은
정확한 합이 `12449.99999999999997` 이라, 합산 후 반올림하면 12,450 이지만
구간별로 반올림하면 12,449 가 됩니다.

빈 문자열(`""`)은 Jackson 이 예외 없이 `null` 로 바꾸므로 `@NotNull` 로 막았습니다.
이게 없으면 걸음수가 빠진 데이터가 조용히 0 으로 집계됩니다.

### 3. float 로 계산된 값이 그대로 들어 있습니다

`0.29999998`, `9.759994` 같은 값이 있습니다. 부동소수로 누적하면 원본 합계와 어긋나므로
저장과 집계를 모두 `DECIMAL` 로 수행하고, 응답에서만 실수로 변환합니다.

### 4. 같은 데이터가 다시 올라올 수 있습니다

App to App 수집은 네트워크 실패나 앱 재시작으로 재전송이 일어나는 것이 정상 흐름입니다.
그대로 저장하면 걸음수가 두 배가 되므로 중복 차단을 세 겹으로 두었습니다.

| 단계 | 수단 | 역할 |
|---|---|---|
| 1 | `payload_hash` 조회 | 같은 payload 통째 재전송을 즉시 판별 |
| 2 | Redis `SET NX` | 이미 처리한 구간을 저장 전에 제외 |
| 3 | `dedup_key` UNIQUE | 위 둘을 통과한 동시 요청의 최종 방어선 |

`dedup_key` 에 **측정값은 넣지 않습니다.** 단말이 같은 구간의 값을 보정해 다시 보낼 수 있는데,
값을 키에 포함하면 보정 전후가 서로 다른 측정으로 취급되어 중복 저장됩니다.

저장에 실패하면 Redis 표시를 되돌립니다. 표시만 남고 저장이 안 되면
단말이 다시 보내도 건너뛰어 데이터가 영영 유실됩니다.

## 주요 설계 결정

### 집계 테이블을 따로 두고, 갱신은 재계산으로

조회는 자주 일어나는 반면 원본은 한 사람당 한 달에 수천 건씩 쌓입니다.
수집 시 **영향받은 날짜만** 원본에서 다시 합산해 UPSERT 합니다.

"기존 값에 더하기"가 아니라 "그 날짜 전체 재계산"입니다. 누적 방식은 같은 데이터가 두 번 반영되면
값이 어긋나고, 한 번 어긋나면 원본과 대조하기 전까지 알아챌 수 없습니다.

월별 집계는 원본이 아니라 **일별 집계를 더합니다.** 사용자가 두 화면을 함께 보므로
월 합계와 일별 값의 합이 어긋나면 오류로 받아들이기 때문입니다.

### 원본 저장은 JDBC 배치

`health_records` 는 `AUTO_INCREMENT` 를 쓰는데, Hibernate 는 IDENTITY 전략에서 생성된 키를
즉시 받아야 하므로 INSERT 를 묶지 못합니다. 1,500 건이면 1,500 번의 INSERT 가 나갑니다.
JDBC 배치로 500 건씩 나눠 보내면 드라이버의 `rewriteBatchedStatements` 와 맞물려
여러 행이 하나의 구문으로 합쳐집니다.

### 시각 컬럼을 세 종류로 구분

| 컬럼 | 기준 | 의미 |
|---|---|---|
| `start_at_utc` / `end_at_utc` | UTC | 단말이 측정한 시각 |
| `measured_date` | KST | 집계 기준일 |
| `created_at` / `updated_at` | 서버 로컬 | 서버가 저장한 시각 |

MySQL `DATETIME` 은 타임존을 담지 않아, 어떤 기준의 시각인지는 저장하는 쪽이 정해야 합니다.
드라이버에 맡기면 세션 타임존(`+09:00`)이 적용되어 `start_at_utc` 컬럼에 KST 값이 들어갑니다.
`AttributeConverter` 로 UTC 를 명시해, 설정이 바뀌어도 저장 값이 달라지지 않게 했습니다.

### Redis 를 쓰는 세 곳

| 용도 | 키 | 이유 |
|---|---|---|
| 리프레시 토큰 | `auth:refresh:{memberId}` | JWT 는 발급 후 서버가 통제할 수 없다. 저장된 값을 지우면 세션이 끊긴다 |
| 수집 멱등성 | `health:dedup:{hash}` | 1,500 건을 전부 INSERT 시도한 뒤 예외로 거르는 비용을 줄인다 |
| 조회 캐시 | `health:summary:...` | 같은 구간을 반복 조회하는 부하를 줄인다 |

리프레시 토큰은 원문이 아니라 SHA-256 해시를 저장합니다. 저장소가 노출되어도 그 값만으로는
재발급 요청을 만들 수 없습니다.

조회 캐시의 무효화는 **삭제가 아니라 버전 증가**로 합니다. 캐시 키에 조회 구간이 들어가
한 레코드키에 수많은 키가 생기는데, 패턴 삭제(`KEYS`/`SCAN`)는 Redis 를 멈추게 하거나
그 사이 생긴 키를 놓칩니다. 하나라도 놓치면 사용자가 옛 걸음수를 계속 보게 됩니다.
레코드키별 버전을 캐시 키에 포함시키면 무효화가 명령 한 번으로 끝나고, 놓칠 키가 없습니다.

무효화는 **트랜잭션 커밋 이후**에 실행합니다. 커밋 전에 올리면 다른 요청이 새 버전으로 조회해
아직 커밋되지 않은 옛 값을 캐시에 눌러앉힙니다.

### 인증

액세스 토큰 30분, 리프레시 토큰 14일입니다. 토큰에는 회원 식별자와 용도만 담습니다.
JWT 페이로드는 서명만 되어 있을 뿐 암호화되지 않아 누구나 열어볼 수 있으므로
이메일 같은 개인정보를 넣지 않습니다.

액세스와 리프레시가 같은 키로 서명되므로 용도(`type`)를 클레임에 넣어 구분합니다.
이게 없으면 유효기간 14일짜리 리프레시 토큰을 그대로 API 인증에 쓸 수 있습니다.

로그인 실패는 "없는 이메일"과 "틀린 비밀번호"를 구분하지 않습니다.
구분해 알려주면 어떤 이메일이 가입되어 있는지 확인하는 수단이 됩니다.

## 구현 중 만난 문제

### Spring Boot 4 에서 Flyway 설정이 조용히 무시됩니다

Boot 4 는 자동설정이 모듈별로 분리되어, `flyway-core` 만 넣으면 `spring.flyway.*` 설정이
동작하지 않습니다. autoconfigure jar 를 열어보니 Flyway 클래스가 하나도 없었습니다.
`org.springframework.boot:spring-boot-flyway` 를 명시적으로 추가해야 마이그레이션이 실행됩니다.
`FlywayMigrationStrategy` 의 패키지도 `org.springframework.boot.flyway.autoconfigure` 로 옮겨졌습니다.

### Jackson 3 으로 올라갔습니다

패키지가 `com.fasterxml.jackson` 에서 `tools.jackson` 으로 바뀌었습니다.
`ObjectMapper` 를 직접 쓰는 코드(보안 필터의 오류 응답, 조회 캐시)에서 import 경로가 다릅니다.

### 미매핑 경로가 500 으로 응답되던 문제

전역 예외 처리기의 catch-all 이 `NoResourceFoundException` 을 삼켜 404 가 500 이 되고 있었습니다.
Spring MVC 가 상태 코드를 이미 정해 둔 예외(`ErrorResponse` 구현체)는 그 상태를 존중하도록 고쳤습니다.
클라이언트가 서버 장애로 오해하고 재시도하는 것을 막습니다.

### 같은 초에 발급된 토큰이 동일해 회전이 무력화되던 문제

JWT 의 `iat`/`exp` 는 초 단위라, 같은 회원이 같은 초에 발급받으면 나머지 클레임이 같아
**바이트 단위로 동일한 토큰**이 만들어집니다. 재발급해도 이전 리프레시 토큰과 값이 같아
토큰 회전이 전혀 동작하지 않았습니다. `jti`(UUID)를 넣어 항상 유일하도록 했습니다.

단위 테스트로는 드러나지 않고, 실제로 두 번 연속 호출해야 보이는 문제였습니다.

163 개. 실제 MySQL·Redis 에 붙어 동작합니다.

| 대상 | 내용 |
|---|---|
| 페이로드 정규화 | 제공된 4개 파일 4,710 구간을 파싱해 원본 합계와 대조 |
| 수집 | 실제 파일 업로드, 재전송 멱등성, 캐시·이력을 무력화해도 DB 제약이 막는지 |

| 인증 | 토큰 회전, 리프레시 토큰으로 API 접근 차단, 변조 토큰 거부 |

기대값은 코드가 계산한 값이 아니라 **원본 JSON 을 직접 합산해 구한 값**을 씁니다.
코드 결과를 기대값으로 쓰면 로직이 틀려도 테스트가 통과하기 때문입니다.

## 남은 과제

- 회원이 없을 때 비밀번호 검증을 건너뛰므로, 응답 시간 차이로 가입 여부를 추측할 여지가 있습니다.
  응답 내용은 동일하게 맞췄습니다.
- 로그아웃 후에도 이미 발급된 액세스 토큰은 만료(30분)까지 통과합니다.
  서명만으로 검증되는 JWT 의 특성이며, 유효기간을 짧게 둔 이유가 이것입니다.
- 칼로리는 `health_records.calories` 가 `DECIMAL(10,4)` 라 저장 시점에 4자리로 반올림됩니다.
  원본 JSON 의 정확한 합과 0.0001 kcal 수준의 차이가 생길 수 있습니다.
- 측정 항목이 `steps` 하나뿐입니다. 심박·수면으로 확장하려면 `data_type` 별 정규화 규칙과
  집계 컬럼 설계가 추가로 필요합니다.
